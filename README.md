# VoxBraid

VoxBraid 是一个面向 iPad 浏览器的环境音实时翻译工具。它持续采集周围声音，将源语言转写和目标语言翻译以双语字幕形式实时展示。

项目当前处于设计和最小可用版本（MVP）准备阶段。

## 当前实现状态

最小实时翻译链路已经进入可运行阶段：

- SvelteKit + TypeScript + `adapter-node` 工程骨架
- 服务端使用 `OPENAI_API_KEY` 创建 Realtime Translation 短期客户端凭证
- 浏览器采集麦克风并通过 WebRTC 直连 OpenAI
- 分别处理源语言和目标语言字幕增量事件
- 提供目标语言选择、开始、停止、连接状态和错误提示
- 可取消尚未完成的启动流程，避免停止操作被异步连接覆盖
- 临时 WebRTC 断线先进入等待恢复窗口，期间依赖浏览器自行恢复；超时或明确失败后终止会话
- 初始 WebRTC 连接长时间未建立时主动超时，避免界面无限停留在连接中
- 停止时请求 OpenAI 冲刷剩余字幕，收到关闭确认或短超时后释放连接和麦克风
- 翻译期间尽力申请 Screen Wake Lock

真实账户已经完成短期凭证签发、浏览器麦克风、Translation WebRTC SDP 握手和英文到中文字幕验证。真实 iPad Safari 的长会话、前后台切换和网络抖动仍需继续验证。

## 本地运行

项目要求 Node.js 22 和 pnpm 11。仓库包含 `.nvmrc` 与锁文件：

```sh
nvm use
corepack pnpm install
```

复制配置模板并在本机填写服务端 API Key；不要提交或分享 `.env`：

```sh
cp .env.example .env
```

```dotenv
OPENAI_API_KEY=sk-...
```

启动开发服务：

```sh
corepack pnpm dev
```

打开 `http://localhost:5173`，选择目标语言并点击“开始翻译”。浏览器会请求麦克风权限。OpenAI 正式 API Key 仅由 SvelteKit 服务端读取；浏览器只获得短期客户端凭证。

### 录音回放测试

开发环境可打开 `http://localhost:5173/?audio-test=1`，选择一段本地录音，让它代替麦克风作为 WebRTC 音轨。录音只播放一次，文件结束后自动停止。日常验证使用几段 5–20 秒的录音，覆盖连接、原文、译文和正常关闭；偶尔再使用一段约 1–3 分钟的完整录音检查连续表现。

测试面板的折叠区也提供“录制新的测试片段”：展开后开始录音，朗读几句公开内容，再点“停止并保存”。浏览器会把录音下载到本机，并立即将它选为当前回放文件。需要重复使用时，可以把下载的文件移到仓库根目录的 `local-recordings/`。仓库只纳入两段固定回归夹具 `hello-can-you-hear-me.webm` 和 `park-story.webm`，该目录下其他临时录音默认被 Git 忽略。也可以直接选择电脑上其他位置已有的录音。

文件只在浏览器中解码，不会上传到 VoxBraid Node；音频仍会通过真实 WebRTC 连接发送至 OpenAI。

达到时限、录音自然结束或用户手动停止后，页面生成可下载的诊断报告。报告只包含状态变化、运行时长、字符数、错误、后台时长和 `deltasAfterClose`，不包含录音名称、字幕正文、thread ID 或 run ID。该模式使用真实 Realtime Translation API，会按音频时长产生费用；模型能力和当前计费方式以 [OpenAI 官方模型页面](https://developers.openai.com/api/docs/models/gpt-realtime-translate) 为准。

项目采用三层测试：

1. 日常单元测试、事件 fixture 和浏览器持久化验收不连接 OpenAI，用于验证事实 reducer、阅读投影、Run 生命周期、视图裁剪、刷新恢复和新建会话。
2. 录音回放测试连接真实 OpenAI：日常只跑数秒到数十秒，偶尔跑一段约 1–3 分钟的完整录音，用于验证 WebRTC、字幕事件和关闭时序。
3. iPad 真机只在关键功能、较大生命周期改动和阶段性回归时执行，用于验证麦克风收音质量、权限弹窗、锁屏、后台挂起、Wake Lock、页面回收、功耗和真实网络切换等桌面无法可靠模拟的行为。

浏览器 API 的测试替身从 Playwright `addInitScript` 注入，不在应用页面中增加运行时门控；这样可以驱动真实的 Wake Lock 和页面生命周期代码，同时保证替身不进入生产包。对无法可靠制造的真实 WebRTC 网络故障采用分层覆盖：客户端单元测试验证 `connection-degraded` 的产生和宽限计时，浏览器测试验证页面对该状态的消费，共享接口和 `ConnectionStatus` 类型负责锁定两层契约。

真实 Realtime 冒烟测试默认跳过，不会因普通测试命令产生费用。只有明确设置开关时才会读取本地固定录音、连接 OpenAI 并断言收到原文和译文：

```sh
corepack pnpm exec playwright-core install chromium-headless-shell
corepack pnpm exec playwright-core install-deps chromium-headless-shell
corepack pnpm test:persistence
RUN_REALTIME_TEST=1 corepack pnpm test:realtime
```

前两条是首次运行所需的本地无头浏览器及系统依赖安装。`test:persistence` 使用隔离的浏览器上下文和仅开发环境可启用的假 Realtime 输入，驱动真实页面完成开始、暂停继续、多 Run、新建 thread、连接降级与恢复、周期与 `pagehide` checkpoint、刷新修复、连接失败保存和 IndexedDB 超时降级；它不连接 OpenAI，也不产生费用。真实链路测试默认使用 `local-recordings/hello-can-you-hear-me.webm`。两条固定录音会额外检查少量稳定的名词或动词；每侧命中约三分之二即可通过，不做逐字比较，以容忍正常的标点、措辞和识别差异，同时确认返回内容确实来自测试语料。可以通过 `REALTIME_TEST_AUDIO` 指定其他文件，通过 `REALTIME_TEST_LANGUAGE` 修改目标语言；新录音可用逗号分隔的 `REALTIME_TEST_SOURCE_KEYWORDS` 和 `REALTIME_TEST_TRANSLATION_KEYWORDS` 指定预期关键词。在非标准环境中可用 `CHROME_PATH` 指定原生 Linux 浏览器。终端默认只打印通过状态和关键词覆盖率；需要查看完整字幕时显式设置 `REALTIME_TEST_VERBOSE=1`。该测试只借用无界面浏览器提供 WebRTC 媒体运行时，不操作 VoxBraid 页面，也不验证录音按钮等界面行为。

## 实现目标

第一版聚焦一个简单、通用的闭环：

```text
环境音输入
  → 实时语音识别
  → 实时翻译
  → 原文与译文对照显示
```

主要使用场景是用户在 iPad 上通过 Safari 或 Chrome 打开 HTTPS 网页，允许麦克风权限后，将设备作为随身实时字幕和翻译终端使用。

“环境音”是项目的基本抽象。第一版不把产品限定为课堂、讲座或会议，也不预设说话人数和内容类型。

## MVP 范围

- 开始和停止麦克风采集
- 在同一个翻译会话中暂停收音并继续追加新的收音片段
- 显示连接、收音、翻译和异常状态
- 连续显示源语言实时字幕
- 连续显示目标语言实时翻译
- 支持至少一个明确的翻译方向，例如英语到中文
- 将连续增量文本整理成可阅读的双语片段
- 保存翻译会话及整理后的字幕片段
- 使用 IndexedDB 保存尚未提交的字幕，刷新、短暂断网或页面被系统回收后能够恢复
- 翻译期间请求 Screen Wake Lock，并提供适合低亮度使用的深色界面
- 检测页面可见性、麦克风轨道和 WebRTC 状态，明确提示中断并在回到前台后恢复
- 针对 iPad Safari 优先验证，并兼容 iPad Chrome

第一版暂不处理：

- 原生 iOS/iPadOS App 和 App Store 上架
- 同一台 iPad 上其他 App 的系统音频采集
- 多人说话人分离和重叠发言归属
- 自动判断双向对话中每句话的翻译方向
- 服务端音频中转或转码
- 播放或外放翻译语音
- 默认保存原始录音
- 锁屏后继续采集麦克风（Web 版本不承诺此能力）
- 面向其他用户的注册、计费、精细额度和并发控制
- 复杂术语库、自动后台摘要、批量知识提取和其他后台分析
- Kubernetes、独立 Worker 集群等提前扩容设计

## 总体架构

```text
                         ┌────────────────────────┐
                         │ OpenAI Realtime        │
                         │ 识别、翻译和字幕事件    │
                         └───────────▲────────────┘
                                     │ WebRTC
                                     │ 连续音频与实时事件
┌──────────────────────┐             │
│ iPad 浏览器           ├─────────────┘
│ Svelte 客户端         │
│ 麦克风、字幕和本地恢复 │
└──────────┬───────────┘
           │ HTTPS：鉴权、创建会话、批量保存字幕
           ▼
┌──────────────────────┐        ┌──────────────────────┐
│ Railway               │        │ Supabase             │
│ SvelteKit Node 服务   ├───────►│ Postgres / 后续 Auth │
│ 无状态控制层和网页     │        │ 可选 Storage         │
└──────────────────────┘        └──────────────────────┘
```

实时音频路径为“浏览器 ↔ OpenAI”，不经过 Railway Node 或 Supabase。Node 和数据库不应成为实时翻译能否继续运行的同步依赖。

## 技术选型

| 层级          | 选型                        | 主要职责                                   |
| ------------- | --------------------------- | ------------------------------------------ |
| Web 应用      | SvelteKit + TypeScript      | 页面、客户端交互及服务端 API               |
| 包管理器      | pnpm                        | 依赖安装、脚本和工作区管理                 |
| 浏览器媒体    | `getUserMedia` + WebRTC     | 麦克风采集和实时音频传输                   |
| 浏览器持久化  | IndexedDB + Dexie           | 保存未提交字幕和恢复信息                   |
| 实时 AI       | OpenAI Realtime Translation | 源语言识别和目标语言翻译                   |
| 上下文问答    | OpenAI Responses API        | 基于已保存字幕进行总结、追问和结构化整理   |
| Node 运行方式 | SvelteKit `adapter-node`    | 将前端和 API 构建为一个 Node 服务          |
| 应用部署      | Railway                     | 承载 SvelteKit Node 应用和后续轻量后台任务 |
| 持久化        | Supabase Postgres           | 会话和字幕；以后可扩展用户与任务状态       |
| 身份          | 初期采用简单的单用户保护    | 以后开放使用时再接入 Supabase Auth         |
| 文件存储      | Supabase Storage（按需）    | 后续可能产生的录音或导出文件               |

当前 OpenAI 官方模型目录和客户端凭证示例已经确认存在 `gpt-realtime-translate` 与 `gpt-realtime-whisper`。计划使用前者进行实时翻译，并配置后者产生源语言字幕。仍然应在开发第 0 步使用真实账户完成最小连接测试，不只依赖文档设计。

ChatGPT 订阅与 OpenAI API 使用量是两套独立的产品和账单，部署后的 API 调用需要单独配置 Platform 项目、密钥和项目级预算提醒。第一阶段仅供自己使用，不实现面向其他用户的产品计费。

项目运行时只使用 Node.js 工具链，不依赖 Conda、Python 或 Rust。开发和部署统一使用当前 Node LTS 与 pnpm。

## 各层职责

### iPad 浏览器

- 请求并管理麦克风权限
- 创建和关闭 WebRTC 连接
- 将麦克风音轨直接发送给 OpenAI
- 接收源文本、译文和连接状态事件
- 聚合字幕增量并形成可保存的片段
- 将待提交片段写入 IndexedDB，在短暂断网、刷新或页面恢复后重试
- 监听 `visibilitychange`、`pagehide`、MediaStreamTrack `mute` / `unmute` 和 WebRTC 连接状态
- 在翻译期间申请 Screen Wake Lock；锁屏或进入后台后不假设麦克风仍在工作

### SvelteKit Node

- 提供页面和静态资源
- 对自用入口和凭证接口提供简单保护
- 使用正式 OpenAI API Key 创建短期客户端凭证
- 创建、归档和查询翻译会话及其收音片段
- 批量接收字幕片段
- 根据用户选择的字幕范围处理 GPT 问答支线，不冻结完整上下文副本
- 在调用 GPT 前持久化 pending，并在返回浏览器前事务性保存完整回答和 usage
- 读取支线时由服务端修复超过配置期限的遗留 pending
- 记录使用时间、错误和成本估算
- 后续创建后台分析任务

Node 采用无状态设计：不能把活动会话或唯一字幕副本只保存在某个 Node 进程的内存或本地磁盘中。实例重启或替换后，另一实例应能根据客户端和数据库状态继续处理请求。

### Supabase

- 保存跨设备、跨实例和跨重启需要保留的数据
- 为会话和字幕提供数据库访问控制
- 开放给其他用户时，通过 Supabase Auth 和 Row Level Security 隔离用户数据
- 后续按需保存文件和后台任务状态

Supabase 不接收每一个实时字幕 delta。客户端先聚合成片段，再批量写入数据库，以降低写入频率并避免数据库进入实时媒体关键路径。

## 核心会话模型

产品层将原始转录和模型生成内容分开：

```text
翻译会话 Translation Thread
├── 收音片段 Capture Run
│   └── 字幕片段 Transcript Segment
└── GPT 对话支线 Assistant Branch
    └── 对话消息 Assistant Message
```

翻译会话类似一个可持续追加的聊天会话。暂停只结束当前收音片段，不清空或关闭翻译会话；继续时创建新的收音片段。用户可以基于截至某处或选定范围的字幕创建 GPT 问答支线，但模型回答不会写回原始转录。底层 OpenAI session 和 conversation 都只是远端资源，不作为产品身份。

完整字段、生命周期、暂停语义、断线重建和持久化约束见 [`docs/session-model.md`](docs/session-model.md)。从可重建 IndexedDB 过渡到 Supabase migration 的阶段划分见 [`docs/persistence-roadmap.md`](docs/persistence-roadmap.md)。

## 初步数据模型

### `translation_threads`

- 产品会话 ID、用户 ID 和可选标题
- 默认目标语言、创建时间、更新时间和归档状态

### `capture_runs`

- 所属会话、顺序号和自动恢复来源 run
- 实际目标语言和运行状态；历史记录在 run 分隔处标明目标语言
- 创建、媒体开始、最后活动和结束时间，以及结束时间是否为估算
- 音频时长、页面隐藏检查点、客户端平台和结构化错误信息
- 源文本与译文各自的完整追加流快照，作为分段失败时的文本兜底

### `transcript_segments`

- 所属收音片段和顺序号
- 源语言文本和目标语言文本
- `approximate` 或 `unpaired` 的展示级对齐标记，不声称协议级一一对应
- 可重新计算的投影 revision；仍被消息上下文范围引用的历史 revision 暂时保留
- 创建和更新时间

### `assistant_branches`、`assistant_messages`（Supabase 后续）

- 所属翻译会话和独立的多轮对话历史
- Message 冗余会话 ID，并由复合外键约束 branch 必须属于同一会话
- 用户问题、非流式 MVP 回答、重试关系及预留的流式生成状态
- 用户问题保存轻量字幕范围；不建立全文 context snapshot
- 可选的 OpenAI conversation 与 response 关联 ID
- 每次调用独立保存 usage 状态、模型和 token 用量；自用阶段按当前价格近似估算成本
- 多选范围需要关系映射时再增加 `assistant_message_context_segments`

### `analysis_jobs`（后续）

- 所属用户和会话
- 任务类型、状态和进度
- 输入、输出及错误信息
- 重试次数和时间信息

## 已确定的讨论决策

1. **先做 Web App。** iPad Safari 是第一兼容目标，Chrome 是兼容目标；暂不开发原生 App。
2. **保留完整 Node 应用。** 曾考虑“纯静态前端 + Supabase Edge Function”，但考虑到额度控制、历史查询和未来后台任务，最终选择在 Railway 部署完整的 SvelteKit Node 服务。
3. **实时音频绕过 Node。** 浏览器通过 WebRTC 直连 OpenAI，Node 只承担可信控制面，不承担连续媒体流量。
4. **正式 API Key 永不进入浏览器。** Node 使用正式密钥为已授权用户创建短期客户端凭证。
5. **跨设备和服务端权威状态最终进入 Supabase。** 领域结构仍在变化时先用可恢复的 IndexedDB 验证模型；字段稳定后再固化首版 migration。Node 可以横向扩容或随时重启，不依赖 sticky session 和实例本地状态。
6. **数据库不在实时链路上。** 保存失败不应中断正在进行的翻译；字幕在客户端聚合后批量持久化。
7. **先保存文本，不默认录音。** 录音会增加隐私、存储、上传恢复和成本问题，等核心闭环稳定后再决定。
8. **字幕对齐采用近似分段。** 源文本和译文是两条连续增量流，不能假设天然逐句一一对应；UI 需要结合标点、停顿和时间信息形成双语片段。
9. **不提前绑定具体场景。** 产品以环境音实时翻译为核心，课堂、讲座和会议只是可能的使用方式。
10. **第一版字幕优先，不播放译音。** 这样可以避免外放被麦克风重新采集形成反馈，也不需要在远场收音和回声消除之间提前做取舍；以后可以优先增加耳机播放。
11. **第一阶段仅供自己使用。** 暂不实现多用户注册、产品计费和复杂额度控制，但 API、会话和数据表不应堵死以后增加用户边界的可能。
12. **Web 版本通过防锁屏保持连续运行。** Safari/PWA 不保证锁屏后的麦克风和 WebRTC 采集；翻译时使用 Screen Wake Lock，并提供深色低亮度界面。若锁屏采集成为硬需求，再评估原生 iPad App。
13. **可靠性优先于激进静音裁剪。** 模型按音频时长计费，但远场客户端 VAD 可能裁掉弱声和句首。MVP 先提供手动暂停并测量真实静音计费行为，再决定是否增加可配置的本地 VAD。
14. **未提交数据进入 IndexedDB。** 纯内存只能作为短期缓冲，不能承担 iPad 页面回收和刷新后的恢复。
15. **当前不承诺主动重连。** 临时断线时先等待浏览器恢复；超时后结束当前收音片段，产品会话和已有字幕继续保留。以后自动重建连接时，在同一产品会话中创建新的收音片段并获取新的短期凭证。
16. **暂停不结束产品会话。** 暂停会冲刷剩余字幕并关闭当前媒体连接；继续时在同一翻译会话中追加新的收音片段。字幕不得跨越暂停断点自动合并。
17. **上下文问答是独立支线。** 原始转录是事实主线；GPT 摘要和问答保存在独立 branch 中。用户消息只记录轻量字幕范围，不冻结或复制请求时全文；第一版使用文本输入，语音命令以后通过显式按住说话模式触发，不从环境音中自动猜测。
18. **字幕事实与阅读投影分离。** 实时路径只追加并展示完整原文流和译文流；历史 segment 由两条字符串分别按标点切块、按顺序近似组合，多出的尾部标记为 `unpaired`。`elapsed_ms` 不参与跨流配对，投影不好看时可以重算，不能因分段失败丢失事实文本。
19. **ID 由应用层生成。** 离线 thread、run、segment 由浏览器生成 UUID，服务端 branch 和 message 由 Node 生成 UUID；显式 sequence 负责排序，多端并发以后由服务端协调。
20. **重新分段采用版本化投影。** 新 revision 的全部 segment 和当前版本指针必须在同一个 IndexedDB 或数据库事务中提交；仍被 assistant message 上下文范围引用的旧版本暂时保留，无引用的旧版本以后可以整组清理。
21. **GPT 上下文不静默截断。** Node 在调用前计算完整请求的 token；超过模型与产品预算时提示用户缩小范围。参与预算计算和实际发送的必须是同一份内存文本。每次调用和重试分别保存最终状态、模型和 token 用量。
22. **GPT 问答先采用非流式持久化闭环。** Node 先保存 pending，再调用 Responses API，随后在事务中写入完整回答和 usage 后才返回浏览器。遗留 pending 由 Node 按可配置期限判为 `failed + unknown`；流式输出推迟到 8b。
23. **本地 schema 先允许重建。** Dexie 阶段只保存 thread、run、segment；第一次 schema epoch 变化前先提供 JSON 导出，且不自动删除旧库。一旦产生不愿丢失的真实内容，就改用正式 Dexie upgrade。
24. **Supabase migration 延后固化。** 字段稳定后先写声明式 schema，再生成和验证首版 migration；远端保存重要数据后只追加迁移，不再重写历史。
25. **自用阶段不保存价格快照。** 模型和 token 用量是持久事实，费用只按当前配置近似展示；面向其他用户计费时再增加不可变价格和正式对账。
26. **测试按事件 fixture、真实录音回放和 iPad 真机分层。** 日常开发优先使用无费用的事件 fixture；真实接口回归使用 5–20 秒固定录音，连续表现只偶尔使用约 1–3 分钟的完整录音；只有关键或较大改动以及阶段性回归才要求真机。回放不循环，两段公开语料的固定录音进入 Git 以保证测试可复现，其他临时录音仍被忽略；录音和字幕正文不进入默认诊断报告。

## iPad 锁屏与后台边界

普通网页无法声明 iOS 原生的 Background Audio 能力，因此不能把“锁屏后继续采集麦克风”作为 Web MVP 的功能承诺。即使某些系统版本或特定状态下连接暂时没有断开，也必须按随时静音、挂起或被系统回收来设计。

Web MVP 采用以下策略：

- 用户点击开始翻译后请求 Screen Wake Lock，避免设备自动锁屏
- 提供几乎全黑的低功耗字幕界面，并提示用户调低系统亮度
- 页面隐藏时立即记录可见性检查点并持久化当前文本，但不把 `hidden` 本身当作媒体已经中断
- 回到前台后检查轨道和连接；有效时继续当前收音片段，失效时结束该片段并由用户操作触发重建
- 重建前后的字幕作为不同连续性区间保存，避免把中断期间误标为“无讲话”

如果实际需求是用户主动锁屏后仍连续收音，技术路线需要升级为原生应用。原生 iOS/iPadOS 可以使用 `AVAudioSession.Category.record` 或 `playAndRecord`，并声明 `UIBackgroundModes=audio`，在锁屏后继续录音。Web 与原生可以复用 Node、Supabase、数据模型和大部分产品逻辑，但麦克风及后台生命周期需要原生实现。

## 以后开放给其他用户时

当前架构保留下列扩展点，但不在自用 MVP 中实现：

- Supabase Auth、用户隔离和 Row Level Security
- 每用户并发、时长、日/月额度和产品计费
- 服务端用量对账、预算告警和异常会话检测
- 客户端凭证签发审计和滥用防护
- 会话最大时长、强制重连或其他可中止活跃会话的机制

短期客户端凭证只能限制新会话的创建。OpenAI 官方当前说明：凭证过期后，已经建立的翻译会话仍可继续，所以将来不能只靠“短 TTL + 续期检查”限制一个正在运行的会话。公开服务前必须重新验证届时可用的活跃会话控制方式，并设计硬性的用量止损。

## 建议实施顺序

0. 使用真实 OpenAI Platform 项目确认模型权限、创建短期凭证，并跑通最小 WebRTC 翻译连接。
1. 使用 pnpm 创建 SvelteKit + TypeScript + `adapter-node` 项目骨架。
2. 使用模拟事件完成 iPad 双语字幕界面和状态流转。
3. 建立服务端短期凭证接口，跑通真实 WebRTC 翻译闭环。
4. 按核心会话模型实现 thread、run、segment 领域类型、无损双流事实 reducer、独立阅读投影和暂停继续。
5. 使用 Dexie 接入三层转录本地恢复、事务检查点和 JSON 导出；开发初期允许 schema epoch 重建。
6. 通过 HTTPS 在真实 iPad 上验证现场环境音、较长会话、Screen Wake Lock、前后台切换、锁屏恢复、功耗和 Safari 页面回收。
7. 字段稳定后编写 Supabase 声明式 schema，生成并验证首版 migration；身份系统先采用满足自用需求的最小方案。
8. 实施 GPT 8a：先完成轻量上下文范围、非流式问答、预算拒绝、pending 恢复和 usage 记账。
9. 实施 GPT 8b：验证 Node 增量持久化和断连恢复后，再启用流式回答。
10. 核心闭环稳定后，再加入历史记录、术语处理和后台分析；对外开放前增加 Auth、RLS 强化、价格快照和正式计费。

## 接入前仍需确认

- 当前账户是否拥有 Realtime Translation 模型权限，以及真实连接的事件行为
- 短期客户端凭证、翻译会话及 WebRTC 连接各自的有效期和关闭行为
- 不播放远端译音时的客户端处理方式和实际计费行为
- 静音音频是否计费，以及暂停发送媒体的可靠实现方式
- 历史双语阅读投影在真实讲座和多人环境中的可读性
- 自用入口采用哪一种最小身份保护
- 字幕保存频率、离线重试方式和数据保留周期
- 默认翻译方向和可选语言
- 隐私提示、录音状态指示及公共场所使用边界
- Railway 与 Supabase 的区域选择、超时配置和预算告警
